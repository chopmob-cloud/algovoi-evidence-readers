# Run record: AlgoVoi canonicaliser over `jcs-byte-vectors`, revision 2276455

Run on 2026-11-24 against the corpus at its current revision.

**Label: directed.** This run is labelled directed under the corpus's own
protocol, not blind. The first version of the reader was written from the
README's boundary table and RFC 8785, and it failed `utf16-nested-key-order`
on the first attempt; the second version was written after reading `check.mjs`
to understand the verifier contract, which is the driver that decides what the
corpus means. A reader told the boundary cases can still be wrong about the
text; it cannot be evidence about whether the text is determinate from a cold
start. A blind run is the follow-up, not this record.

## Finding 1: under `--profile bounded`, no consistent verifier can pass

The driver applies the admission profile to three families and not to a fourth:

| Family | Profile-aware? | Where |
| --- | --- | --- |
| `canonicalCases` | yes | `entry.bounded === "reject"` is refused under bounded |
| `depthCases` | yes | accept cases printed, reject cases refused, under bounded only |
| `noncharacterCases` | yes | the noncharacter family refused, the neighbour family printed, under bounded only |
| `driftCases` | **no** | `runVerifier(…, pinned)` runs under every profile |

So under the bounded profile the same value must be refused in one family and
printed in another. `exponent-switch` holds `1e-7` and must be refused (its
README row says so: "Both are rejected by the integer-only record profile").
`drift-number-two-digit-exponent` holds `1e-07`, the same value, and must print
`1e-7`. A verifier that admits only integers cannot satisfy both. Three further
drift cases are in the same position: `drift-number-expanded-large` (1e+21),
`drift-number-expanded-small` and `drift-number-exponent-without-sign` (1e+30).

This was isolated, not assumed. With the drift family gated to the `jcs` profile
in a local copy of the driver, and nothing else changed, the same reader passes
the whole bounded run. That copy is a diagnostic and is not published as a fix.

The fix is the maintainer's to choose: either gate the drift loop on the profile
the way the other three families are gated, or state in the README that the
drift family is a byte contract independent of admission and drop the non-integer
cases from it.

## Finding 2: fifteen cases are carried and never read

`cases.json` carries an eighth family, `invalidInputCases`, with 15 entries
across three families: `invalid-utf8`, `byte-order-mark`, `malformed-json`, all
expecting refusal. Nothing reads it:

```
$ for f in check.mjs remint.mjs README.md; do printf '%-12s %s\n' "$f" "$(grep -c invalidInput "$f")"; done
check.mjs    0
remint.mjs   0
README.md    0
```

The driver reports 108 checks and the corpus carries 123 inputs. The 15 are not
exercised, so a verifier that accepts a byte-order mark or an overlong UTF-8
sequence still passes the oracle. This reader refuses all 15 (its stdin decode is
strict UTF-8, and `json.loads` refuses a leading BOM), but nothing in the run
proves that.

## The gates

Eight mutations, each disabling one rule in a copy of the reader, each required
to change a named case. All eight bite: `utf16-key-order` → `utf16-nested-key-order`,
`es6-number-form` → `exponent-switch`, `literal-non-ascii` → `ordinary-unicode`,
`duplicate-keys` → `duplicate-member`, `lone-surrogates` → `lone-surrogate`
(both the explicit check and the strict encode disabled, or the encoder silently
backstops the check), `bounded-integers` → `exponent-switch` under bounded,
`depth-cap` → `depth-array-129`, `noncharacters` → the first noncharacter case.

The last three are targeted at one case each rather than at the whole corpus,
because the drift conflict above stops a bounded corpus run before it reaches
the depth and noncharacter families. That is stated rather than worked around.

## What this record does not establish

- It does not establish that the bounded profile is wrong, only that its driver
  applies it inconsistently, and only as of this revision.
- It does not establish determinacy. This is a directed run.
- It says nothing about any other corpus in `agent-evidence-vectors`, and nothing
  about the wheel that ships `cases.json` from 0.17.7 on.
- It does not exercise the 15 `invalidInputCases`, because no driver does.
