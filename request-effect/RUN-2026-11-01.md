## What was asked and what this is

In `probityai/agent-evidence-vectors#352`, at comment `6549030730`, the maintainer
asked for a reader that did not write the contract or the vectors: a third reader
run over **#377**'s `request-effect-join` contract, compared against its
`expected.json`, and separately over `vectors-refund-connected` and
`vectors-uncertain-effect`.

This directory is the first of those. It is a second implementation of
`request-effect-join-fixture/v1`, written from `docs/INPUT-CONTRACT.md` alone.

Two limits that bound what it proves, stated before the figure:

- **The run is directed.** The author had read the contract text and the case
  table before writing the reader. That says the contract is implementable from
  its own words; it says nothing about whether the text is determinate from a cold
  start.
- **`run_contract.py` was not read.** The reference implementation was left
  unopened so that the reader is a reading of the specification rather than a copy
  of the author's code. This is a claim about how the reader was written, and no
  log can evidence it — it rests on the reader's independent implementation of
  RFC 8785, which the differential test below does check.

## Two bugs the green run did not catch, and one shape the contract does not settle

Both were found by `check_named_probes.py`, on records the corpus never builds.

**1. A boolean was accepted where an integer belongs.** Setting `attempt_seq: true`
still classified `established`, because `True` is an `int` in Python. The reader
now type-checks every preimage field (integers where the contract says integer,
strings elsewhere) and rejects a boolean. This is the same class of defect as the
`ownerEffects: true` fail-open found in the earlier `uncertain-effect` work: a
Python truthiness accident standing in for a declared shape.

**2. A dispatched call under a refusing decision classified `established`.** A
record whose `decision` says `deny`, with an `attempt` and a `completed` result,
came back `established` with `join_established` — the reader checked that a decision
*bound* the call and never that it *permitted* it, except on the rewrite path. The
contract's own wording is "the effective call is bound to a decision that permits
it", so a denied call that ran is not an established join. It now refuses with
`effective_call_not_covered` and a native code `DISPATCHED_UNDER_REFUSAL`.

This one is a **divergence from the contract's letter, chosen deliberately**, and
it should be read as a question to the author rather than a correction:
`request-effect-join-fixture/v1` names **no finding** for "permitted by nothing,
yet dispatched", and its order of checks has no step for it. A reader that followed
the seven steps literally would return `established`, as this one did before the
probe existed. There are two coherent fixes — a new finding such as
`effective_call_not_permitted`, or making step 5 apply to every record and not
only rewritten ones — and choosing between them is the contract author's to make.

## The validation round, and what it changed

A model gate was then run on the reader, and it earned its cost in an unexpected
direction: **the reviewers found nothing that survived checking, and a self-test
found a defect they all missed.**

**Reviewers were first shown a diff they had to reject.** Two mutants were planted —
the type guard removed, the permission check removed — and both were caught at
BLOCKER/HIGH before either reviewer was trusted on the real diff, by NIM and by
Copilot `gpt-4.1`. A CLEAN from a reviewer that has never been shown to fail is not
a result, and the mutants are the only evidence that these two can.

On the real diff:

| Reviewer | Routing verified from | Verdict | Disposition |
| --- | --- | --- | --- |
| NIM `nemotron-3-ultra-550b-a55b` | the gate's own review-file header | `504` on the first attempt, then **10 findings** | 3 acted on, 7 refuted with the reproduction |
| Copilot `gpt-4.1` | `served=gpt-4.1-2025-04-14` in the response | `CLEAN`, in **4 output tokens** | not counted as a review |
| Copilot `gpt-4o` | `served=gpt-4o-2024-11-20` | `CLEAN`, also 4 tokens | not counted as a review |

Both Copilot calls went straight to `api.githubcopilot.com` with the diff in the
request body. A first attempt through `hermes -z "<diff>"` died with
`WinError 206: The filename or extension is too long`, because the prompt travels
on the command line and Windows caps that near 32k characters; the direct call was
the workaround, and each answered `served=<model>` plus the usage block, which is
how the routing and the four-token count were established rather than inferred.

The two CLEANs are recorded and then discounted: a reviewer that emits four tokens
on a 1,400-line diff has not read it. Each was able to answer BLOCKER on a 23-line
mutant, so the model is not incapable — the diff was simply too large for a single
call, which is the same budget lesson as the `mimo` runs at 6,000 output tokens.

**Refuted findings, each with the command that settles it.** These were wrong and
acting on them would have damaged the reader:

- *"`original_result_preserved` is not in the contract's closed set"* — it is; the
  set has 15 members and contains it. One command.
- *"`record.get()` conflates an absent key with a null value, so S-05 and S-06
  collapse"* — they do not: the key-set check runs first, so absent is
  `invalid_input` and null is `established`.
- *"Repairing every ref then expecting answers to change is inverted logic"* — the
  logic is the point: with refs repaired, S-07 stops being a `digest_mismatch`,
  which is exactly the evidence that the digest check is load-bearing.
- *"`corpus_digest_check` is called twice, so it runs twice"* — it is called once
  (line 271). The double call was real but one function away, in
  `corpus_profile_check()`, found on inspection rather than from this finding.
- *"LOW, `run.sh` line 18: Python 3.12 requires the extraction filter, so this
  fails"* — `hasattr(tarfile, "data_filter")` is `True` on 3.12, so the branch is
  taken. Checked with one command.
- *"LOW, the `JCS_BOOLEAN_NOT_NUMBER` raise passes a string where an exception
  expects a native code"* — `InvalidInput.__init__(self, native: str, ...)` takes a
  string, and `_canonical(True)` returns `true` before `_number` is ever reached, so
  the branch is unreachable from the public path.
- *"LOW, the null-read probe's control is missing"* — the probe carries its own
  expected class and findings; the finding is imprecise rather than wrong, and the
  real gap it was circling is item 3 below.

**Fixed:** the `permitting` clause lets the original decision authorise a rewrite,
where the contract's step 5 applies coverage only to a rewritten call. True as an
observation, and it matches the corpus — S-02 is a rewrite whose original decision
permits and is declared `established`, while a covering decision that denies is
still refused. The asymmetry is now pinned by two probes so a later edit cannot
"fix" one half into disagreement with the corpus.

**Also fixed, and no reviewer raised it:** `check_requests_bite.py` called
`corpus_profile_check()` twice, so the check ran twice and the second run's result
was the one printed.

**Fixed and acted on — a no-op loop that claimed an assertion.** A `for cid in
("S-00", "S-05"): pass` sat under a comment saying a null read must never be
reported as unchanged. It asserted nothing. Both cases now check the finding and
count, taking the probes from 19 to 21. This is the one finding out of ten that
was correct, actionable and about something real.

**Fixed, and found only by self-testing the strictness I had added:** the reader
refused a record carrying a `covering_decision` with `attempt: null` as
`invalid_input`, on a rule the contract does not state. The contract's order of
checks reaches dispatch (step 4) before coverage (step 5), so that shape is
`not_established`. This was my own invention contradicting the document I was
implementing, and the ten-case corpus could not see it because it contains no such
record. It is now probe 10.

Probe count went 16 to 21. Re-run after the fixes, both interpreters, both stages
green: 10 of 10, 41 checks, 21 probes, 0 divergences, exit 0.

## Round two: both validators on current code, reconciled

After the first round's fixes, both validators were re-run against current HEAD, on
their terms rather than mine, and every finding was tested before anything changed.

**NIM recovered on its third attempt.** The sequence was `429 Too Many Requests`,
then `504 Gateway Timeout`, then a completed review in 292.4 s with six findings.
Two of the three non-runs were quota/congestion, not the code, and reporting them as
non-runs is the only honest reading: a gate that could not run is not a pass.

**Copilot would not review a diff, but answers questions.** Five per-file chunks of
a whole-diff review returned `VERDICT: CLEAN` in **4, 4, 4, 4 and 9 output tokens** —
abstentions, not findings. The same code answered five *directed* questions at 109,
114, 135, 148 and 155 tokens, each citing the lines it relied on, and all five
correctly confirmed the property asked about. So the mode matters more than the
model: given "review this and report defects" it declines; given "does this code
return `established` for a non-permitted call?" it engages. Both CLEAN results are
recorded as non-reviews.

**Reconciled fix list, all six NIM findings tested:**

| # | Finding | Verdict | Action |
| --- | --- | --- | --- |
| 1 | `corpus_digest_check` comment says it simulates "always passes" while the code makes every digest fail | **real** | comment corrected to match the code |
| 2 | `--expected` as the final argument raises `IndexError` | **real** | exits 2 with a message |
| 3 | The dispatch probe grafts an unbound attempt onto S-09, so the case refuses on `join_chain_broken` and the dispatch check is never exercised | **real** | refs rebound so dispatch is the only gate that can move it |
| 4 | The asymmetry probe expects only `join_established` and would fail on a later-state finding | refuted | the probe helper asserts a **superset**; an extra finding it does not forbid cannot fail it |
| 5 | The hand-written number formatter may deviate on integers above 2^53 | refuted as stated, **but right to worry** | the differential now compares nine boundary values |
| 6 | `run.sh` exits 1 when `rfc8785` is missing, so the run is not hermetic | refuted, deliberately | a skipped differential is the one stage whose absence would let a wrong canonicaliser through |

**And the defect neither validator found**, from extending the differential to the
safe-integer boundary: the number formatter printed the decimal digits of integers
beyond ±(2^53 − 1), which no double holds exactly. A conforming JCS implementation
refuses them, so this reader would have disagreed with every other implementation on
the digest of the same record. Now refused, with nine boundary values compared and
two bite-matrix checks pinning it.

Item 5 is the one worth dwelling on: the finding was wrong about the mechanism and
right about the risk, and following the risk rather than the wording is what produced
the only security-relevant defect of the round.
